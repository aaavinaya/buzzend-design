2026-08-05

Media picking is the SYSTEM picker — our own gallery grid is gone

This one is not a preference, it is a store requirement. Google Play rejected the Android build (version code 101) under the Photo and Video Permissions policy. An app targeting Android 13+ may request the broad media-read permissions (READ_MEDIA_IMAGES / READ_MEDIA_VIDEO) that a bespoke media grid needs only when a system picker is technically insufficient for core functionality. “Pick a few items to post” is exactly the case the policy says must use the picker, and the reviewer's finding said so: “your app only requires one-time or infrequent access to media files.”

The prototype drew its own grid in two places — the camera's gallery tab and the composer's PICK step — so it was the reference for the very thing that got rejected. Both are replaced by a stand-in for the platform's picker, drawn in neutral system chrome on purpose: the most important thing that surface communicates is do not style this. Anything a client could restyle there is something it would have to build itself, which is what caused the violation. iOS has no equivalent mandate, but ships the same component (PHPickerViewController), so one picker suits every client — and it is why the iOS build was approved with the identical design.

  • Picking is no longer a place in the flow. The picker opens over whatever launched it, so it never enters the back stack: dismissing it returns you to the camera or the preview you came from with the selection untouched. There is no “gallery screen” to design, route to, or go back to. Dismissing without choosing is not a failure and must stay silent.
  • Hand the picker the REMAINING allowance, never a constant 10. With 8 photos held it is told 2, so the cap is enforced inside the picker — greyed-out tiles — rather than as a complaint afterwards. At 1 remaining, use the platform's single-item contract: its multi-select variant requires a cap of 2 or more, and a second tap must replace rather than add. At 0, do not open it at all — say why.
  • Restrict to images once anything is selected. A post is up to 10 photos or one video, so after the first item a video could only be refused on return. Don't offer it.
  • The rule now runs on the way OUT, not per tap. The picker can cap a count but cannot express “photos XOR video”, so the selection is folded in afterwards: keep what fits, drop the rest, show one message. Folding accumulates, so 4 picked onto 8 held accepts exactly 2.
  • Nothing is dropped silently. A pick can fail to land three ways — it breaks the rule, it is already in the post, or it isn't a photo/video — and each says so. The duplicate case is the one that is easy to miss and the worst to omit: the picker has no idea what you already hold, so re-picking is easy to do by accident and would otherwise look like a dead tap.
  • These are toasts, not dialogs. A dialog demands a tap to acknowledge a fact the user can already see. Copy is one short clause, no trailing full stop — a toast is read in about a second and cannot be re-read — but still worded like a person: Choose photos or 1 video, One video per post, Up to 10 photos per post, Already in your post, That file isn't supported. Both halves matter; the first drafts were full sentences, and the correction overshot into telegraphese (Already added).
  • “Add more” is a Camera / Gallery sheet, not a jump to the picker. The picker has no camera entry point on any platform, so a “+” wired straight to it silently removes “shoot one more” from the add-more path. Two labelled options, one tap deeper. Its header is centred — the option tiles are centred, so left-aligned text hung off to one side of its own content — and it carries the remaining budget, You can add 7 more photos. Singular at one (“1 more photo”): the sheet shows this every time it opens, so the last slot is the most-read case. That budget and the picker's cap come from one function, so the copy can never promise what the picker then refuses.
  • The “+” tile stays a plain plus. A “+7” counter was tried and dropped — the number is stated in words on the sheet it opens, and the tile reads better as a clean affordance.
  • Reaching the camera from “Add more” is a DIFFERENT screen state. It showed the full new-post camera, which offered three wrong things. Video mode: a clip recorded there could only be thrown away on return, so the whole Photo/Video row goes (a lone “Photo” pill is pointless chrome) and photo mode is forced. The gallery entry: the sheet just offered Gallery, so a second door to it loops back to the option you declined — replace it with an equal-size spacer, since the controls row is space-between and dropping a child drifts the shutter off-centre. The title reads “Add photo”, not “New post”.
  • And the real defect: that screen's ✕ discarded the draft. It was wired to close the composer, so one tap threw away up to 10 photos with no confirmation — and the platform back gesture did the same, because entering from “Add more” leaves the camera as the only entry for a plain back to fall through. Both now return to the draft, and the control is a back affordance rather than an ✕ that means “throw this away”. Only a genuinely empty camera step closes the composer.
  • A video post has no “+” at all — the whole thumbnail strip is hidden — so neither option can be reached in a state where every pick would be refused.

To implement on a new client: delete any bespoke media grid and call the platform picker, passing the remaining allowance as its item cap and an images-only filter once anything is held. Put the “photos XOR video” rule, the messages, the remaining count and its singular/plural in one module that both the picker call and the UI copy read from — the copy promising a budget the picker contradicts is its own bug. Then check the two things that are easy to miss: a re-picked item must be reported, not silently dropped, and leaving the camera while holding a draft must go back to it, never close the composer. Reference implementation (Android): feature/contentcreation/ui/domain/MediaSelection.kt (rules, messages, remaining + plural), ui/navigation/GeneralComposeFlow.kt (picker contract, fold-in, back policy), ui/capture/GeneralCaptureScreen.kt (addingMore state), ui/preview/ComposePreviewScreen.kt (the sheet). The permission removal is pinned by a test — MediaPermissionPolicyTest — because re-adding it breaks no feature locally and only fails at review.

2026-08-04

Exercise marks are now the drawn ILLUSTRATIONS, not line glyphs

Every exercise mark across the prototype was a Lucide-style stroke glyph (Icons.svg('squat')). The app replaced those with the supplied artwork on 2026-07-31 and keeps the stroke glyph only as the unknown-type fallback, so the prototype had drifted from the thing it is supposed to be the reference for. It now draws the same artwork.

Three families, and the choice is per surface — never mixed within one screen. Two drawings of the same squat side by side in different families is the exact bug the shared registry exists to prevent.

  • Nothing to do at most call sites. All six exercises funnel through Icons.svg(name, size), which now returns artwork for squat · pushup · situp · jumping · lunge · walk/footprints. Existing screens picked it up with no edit.
  • Need the old stroke glyph? Icons.svg('squat-line', 18). That is what the app keeps for an unrecognised workout type and for the post-set medallion.
  • Need a specific family? Icons.workout('squat', 40, 'plain') for one surface, or set Icons.artStyle = 'plain' once at the top of a screen that uses one family throughout.
  • Files: docs/assets/workout-art/ — plain SVG, one per exercise per family, so any platform can consume them directly (vector drawable, PDF/SF Symbol-style asset, or <img>). Naming is <exercise>[-outlined|-plain].svg, keyed on the six backend workout codes — WLS steps, PUSHP, SQUAT, SITUP, JJACK, LUNGE — which is the one identifier every client already shares. yoga ships but is unmapped: no yoga workout type exists on the backend, so wiring it would mean inventing a workout the API cannot store.
  • Sizes are optically normalised, and this part is not optional. The postures have wildly different aspect ratios (push-up ~1.95:1 landscape, squat 0.84:1 portrait), so fitting them into one square makes the ink differ by ~2.1×. icons.js ports the app's workoutArtworkOpticalScale verbatim: equal area, not equal width or height — k = √(0.474 / min(r, 1/r)), capped at 1. The slot is always exactly the size you asked for; only the fill changes. In a 40px slot the sit-up draws 40px across and the lunge 27.6px, and that is correct.

To implement on a new client: one shared resolver that answers “what picture goes with this workout code, in which family, at what size”, and pin the family per screen in a single constant rather than at each call. The area-equalising scale must live in that resolver too, so no call site can forget it. Reference implementation (Android): core/designsystem/icon/WorkoutArtwork.kt, with the per-surface families set in FriendsActivity.kt (outlined) and CreateChallengeScreen.kt (plain).

2026-08-04

Create Challenge + challenge cards brought in line with the app

Five changes shipped in the app this round; all five are now here too.

  • Quick start is 9 chips in a two-row carousel, not 4 in a wrapping row. Each exercise has exactly one preset except squats and push-ups, which carry a starter + a full 30-day version so the duration is part of the choice. .cc-quick uses grid-auto-flow:column over two rows, i.e. fill top→bottom then across, so pairs sit above one another and the section stays a constant height however many presets get added. A wrapping row grew to five stacked rows at nine chips and pushed the exercise grid below the fold.
  • Chip icons encode the KIND of preset — rocket = starter, trophy = full 30-day, target = daily number, zap = cardio burst, wand = build your own — not which exercise. They repeat across chips on purpose. Drawing the exercise figure there was tried in the app and rejected: the chip and the grid tile below showed the same drawing twice, and the two squat presets became indistinguishable since only duration separates them.
  • Exercise-type grid: figure 26 → 48px, tile pinned to a 112px min-height so a wrapping 2-line label (“Jumping Jack”) can’t make one box taller than its neighbours.
  • Step 3 draws the exercise figure ONCE. It used to appear three times — the 72px preview tile, a copy in the chip beside it, and a third in the Summary “Exercise” row. The tile keeps it; the chip is text-only; the summary row uses the generic dumbbell mark like every other row in that table.
  • Canonical exercise order everywhere: Steps · Push-ups · Squats · Sit-ups · Jumping Jacks · Lunges. Both the create-challenge grid and the Discover category chips previously had their own order. GET /workouts really does return jumping jacks before sit-ups — the app normalises the catalog once at its cache rather than trusting the endpoint, so do not “fix” these lists back to a server response.
  • Bigger marks on the cards: Discover trending 40 → 54px (card min-height 180 → 192px, which is what keeps every card in the rail the same height), challenge-card tile 40 → 54px with a 42px figure, challenge-detail cover chip 13 → 24px.

Client-agnostic notes: the preset list, the canonical order and the catalog sort are data decisions — put the sort where the workout catalog is cached, not in a screen, or every list that reads it drifts again. Reference implementation (Android): CreateChallengeState.kt (presets), CreateChallengeScreen.kt (layout + step 3), ChallengeRepositoryImpl.workouts() (the catalog sort), DiscoverScreen.kt, MyChallengesScreen.kt, ChallengeDetailScreen.kt. Full per-item rationale: docs/specs/CREATE_CHALLENGE_UI_SPEC.md §10 in the Android repo.

KNOWN GAP

Active-challenge ring: still the prototype's structure, not the app's

The shipped clients draw the exercise figure inside the progress ring at 40pt (ring 56pt) and puts the day count in the meta line. This prototype puts the percentage in the ring centre and the exercise in a small corner badge, now grown 21 → 26px so the illustration is legible. Reconciling the two means dropping the % readout — a design decision, not an icon change, so it is flagged here rather than decided. Affects .chalx on Home and the my-challenges cards.
